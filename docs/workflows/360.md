# 360 video (Insta360 X3)

Part of every install. Cutpoint analyses X3 footage on the small `.lrv` proxy, a
"director" picks a smooth virtual-camera path for each chosen moment, and `clips` / `extend`
render flat 16:9 (or 9:16) clips with ffmpeg `v360` and `sendcmd`. `assemble` and the Resolve
timelines work unchanged. How the director chooses is in [360 director](360-director.md).

Rendering works without any SDK, using the raw dual fisheye ("preview quality": a visible lens
seam along the horizon). For a blended seam, bring your own Insta360 Media SDK; see
[insta360-sdk.md](../insta360-sdk.md). Check it with `cutpoint 360 status`.

## Basic flow

```powershell
cutpoint 360 scan D:\Videos\trip360 --out trip-360        # pano.json: clips, modes, IMU orientation
cutpoint 360 analyze trip-360 --style ski                 # view layer + analyze + events on the .lrv
cutpoint clips trip-360 --max-total 150                   # moments rendered flat, 1920x1080
cutpoint extend projects/trip-360/clips --seconds 4
cutpoint assemble projects/trip-360/clips_ext4s --loudnorm
```

Add `--vertical` to `clips` for 1080x1920. Camera folders are only read.

`360 analyze trip-360 --scan D:\Videos\trip360` runs the scan first, so the first two lines can
be one.

## In the UI

In `cutpoint ui`, New project takes a camera folder or one X3 file (`.insv` or `.lrv`; one file
means just that clip). "Analyze footage" runs `360 analyze <project> --scan <folder>` (with
`--only NNN` for one file) and lists its steps: Read 360 clips, 360 views, Transcription and
ranking, Events and re-rank. The vision rating is not used. The style is `pano.default_style`
(else `ski`) unless the API was given a `ski`-kind style. Moments are previewed through the
director's camera path (see [Director preview](#director-preview-and-camera-path-flags)), with
the raw `.lrv` (dual fisheye) until that is rendered; "Export clips" reframes each one with the [director](360-director.md), as `clips`
does. Without an SDK stitch or a Studio export (on Linux, usually neither), clips are rendered from
the raw fisheye (`dfisheye`, preview quality). It needs what the CLI needs (the `ski` and `events`
extras, the `cutpoint setup` models); a missing one stops the first step with the install hint.
Keep 360 footage and regular videos in separate folders: a folder with both is refused.

### Director preview and camera path flags

When you open a 360 moment, the UI gets its camera path from the
[preview API](#preview-api-python) and renders a flat 640x360 view of the `.lrv` along it in
the background (as `360 director --preview` does). That is the path `360 analyze` cached for it
([Camera paths of the candidates](#camera-paths-of-the-candidates)) when it is current; else one
planned now as `clips` would (no cached path, or settings, layers or Cutpoint's planning code
changed since the analysis); else, when the director cannot plan (footage offline, no IMU), a
level forward view. A director path covers the span it was planned for: the moment and up to
10 s on either side. The raw fisheye plays until the render is ready; a note above the video says
which one you see (and, for a path planned now or a forward view, why), and shows the render's
progress with Cancel. Outside that span (a trim or a seek past it) the raw preview plays. "Play
sequence" plays the raw preview.

The render is kept in `<project>\ui\pano\` and reused, also after a restart, until the path,
the preview format or a pano setting the render reads (such as `pano.imu_offset_s`) changes. A
cancelled or failed render leaves no partial file. With the footage offline even the level
forward view cannot render: the note says so, with the reason (such as `footage offline`), until
the footage is back; then Retry director view renders it. Not built yet:
planning a new path when a
trim goes past the planned span; that part plays the raw preview.

A moment whose cached path is flagged gets word badges on its card (Sky, Whip pans, Spinning,
Many cuts, Wearer, Off target, QA fail). Hover over the card or focus it with the keyboard to see the reasons, with
the measure behind each, such as "looks at the sky (35% of the moment)"; Escape hides them.
Screen readers read them as the card's description, and the note above the video lists them as
text. The flags and their provisional thresholds are those of the
[diagnostics](#camera-paths-of-the-candidates).

### Auto-stitch on export

When your Insta360 Media SDK is found and runs (see `cutpoint 360 status`), "Export clips" first
stitches the recordings behind the chosen moments with `360 stitch` (`--segments` with the
sequence's segments file, or `--clips NNN ...` for automatic picks), then renders the clips from
the stitched equirects. Only recordings that are not stitched yet are stitched; later exports of
the same recordings reuse them. The job log shows the estimate before the stitch starts.

- The SDK stitches whole recordings, so an export can take a long time and needs about 54 GB
  per hour of footage in `pano.stitched_dir`. If the drive would keep less than 20 GB free, the
  stitch is skipped with a WARNING.
- The SDK needs an NVIDIA GPU: without one, the stitch is skipped with a WARNING.
- If the SDK is missing or does not run, there is no NVIDIA GPU, `pano.auto_stitch` is off, the stitch is skipped or it
  fails, the export still finishes from the dual-fisheye preview, with a WARNING in the job log.
  Export then says "Exported from the 360 preview (not stitched)".
- Cancel stops the stitch and the export.

To export without stitching, set `"pano": {"auto_stitch": false}` in `config.json` (see
[configuration](../configuration.md#pano)). It only affects the UI: the command-line `clips`
never stitches.

## Files

One recording is one clip, numbered NNN:

| File | Content |
|---|---|
| `VID_YYYYMMDD_HHMMSS_00_NNN.insv` | Lens 1 plus the IMU trailer |
| `VID_YYYYMMDD_HHMMSS_10_NNN.insv` | Lens 2 (5.7K mode only) |
| `LRV_YYYYMMDD_HHMMSS_11_NNN.lrv` | 1024x512 dual-fisheye proxy, frame-exact with the `.insv` files |

The `.lrv` is the clip's identity for analysis, transcripts and caches. The `.insv` files are
read for the IMU trailer and for rendering.

## Commands

| Command | Does |
|---|---|
| `360 scan <folder>... --out <project>` | Pairs files, reads modes and metadata, builds a horizon-orientation track, writes `pano.json`. Scanning another folder merges clips |
| `360 analyze <project> [--scan <folder>...] [--style S] [--only NNN ...] [--views-only] [--no-events] [--force-views]` | `--scan` first runs `360 scan <folder>... --out <project>` (with `--only`, for those clips alone). Then the view layer, `analyze` on the `.lrv`, the `events` layers and a re-analysis, then a director path for every candidate (see [Camera paths of the candidates](#camera-paths-of-the-candidates)). `--style` defaults to `pano.default_style`, else `ski` |
| `360 status [<project>]` | Whether the SDK is found and runs; with a project, per clip: mode, cached views, the render source `auto` would pick |
| `360 director <project> [--top N \| --ids ... \| --segments FILE] [--vertical] [--preview] [--force]` | Plans director paths without the full render, as JSON in `pano_paths\director\`; `--preview` renders small checks |
| `360 stitch <project> [--clips NNN ... \| --from-clips DIR \| --segments FILE] [--dry-run]` | Stitches whole clips with your SDK. `--dry-run` prints the commands and works without the SDK |
| `360 check <clips_dir>` | Contact sheets of rendered clips, captioned with the director target, yaw and pitch |
| `360 qa <dir> [--fps 2] [--size 640x360] [--json-only] [--paths] [--compare QA_JSON QA_JSON]` | Checks rendered clips or director previews for occluders, too-close people, edge cuts, dark frames, horizon tilt, pans and the `--vl-check` flags of `360 director`; writes `<dir>_qa\qa.json` and contact sheets. `--paths`: the geometric check from the paths alone, into `<dir>_paths_qa\qa.json`. `--compare`: see [Where the two QAs disagree](#where-the-two-qas-disagree) |
| `360 repair <project> --qa FILE [--segments FILE] [--out FILE]` | Turns QA results into a better mix: trims or drops unclean clips and refills the time |

Every `360` subcommand takes `--json`: one [result envelope](../commands.md#json-output) on stdout.

`360 analyze` writes `pano_timings.json` in the project, the seconds of that run alone (an
earlier run's keys are dropped, except by `--views-only`, below): `views` (the view layer's own stats and its `total_s`),
`analyze_s`, `events_s` (not with `--no-events`), `paths_s` (the candidates' director paths),
`scan_s` (with `--scan`) and `total_s`, the whole run from its start, scan included.
`--views-only` leaves `highlights.json` as it was, so it keeps the keys of an earlier file
that times an analysis (with `analyze_s` or `analyze_total_s`), which still describe it (its `total_s` and `scan_s` too), and writes only this run's
`views` and `views_only_s`, the seconds of this run, its scan included; without an earlier
file it writes `views`, `total_s` and, with `--scan`, `scan_s`. `analyze_total_s` is no
longer written (read `total_s`); files from older runs may still have it. If a run fails
(Ctrl+C included) once `highlights.json` has changed, it removes the earlier
`pano_timings.json` rather than leave one that describes another analysis (a file it cannot
remove only gets a WARNING); a failure that leaves `highlights.json` as it was keeps it. `360 scan` on its own adds its `scan_s` to the file.

`360 analyze` warns and exits 0 if the footage is not reachable (offline drive, moved file) by the events re-rank, leaving `highlights.json` without the events; rerun it once the footage is back.

If the footage moved, `clips`, `extend`, `360 analyze`, `360 director`, `360 stitch` and `360 status` read it through `source_remap` (see [configuration](../configuration.md)); the project keeps the original paths.

## Render sources

`--pano-source auto|sdk|studio|dfisheye` on `clips` and `extend`. `auto` takes the best
available per clip.

| Mode | Input |
|---|---|
| `sdk` | A stitched equirect written by `cutpoint 360 stitch` into `pano.stitched_dir`. Needs your own SDK. About 54 GB per hour of footage |
| `studio` | A 2:1 equirect exported from Insta360 Studio into one of `pano.studio_dirs`. Named with the clip's `VID_YYYYMMDD_HHMMSS` stem or `_NNN` number. Trimmed or reframed exports are rejected |
| `dfisheye` | The raw dual fisheye. Always available, preview quality |

Stitch without FlowState: Cutpoint levels the horizon with its own IMU track, and a FlowState
stitch keeps its own heading reference, which makes the framing drift. See
[insta360-sdk.md](../insta360-sdk.md).

When the 360 clips of one `clips` run (also `edit` and `assemble <project>`) are not rendered
the same way, one WARNING lists them (`pano_mixed_sources` with `--json`, `files` naming the
360 clips (empty for a temporary export: `assemble <project>`, `edit --no-keep-clips`)): stitched (`sdk`, `studio`)
and dual fisheye sources mixed in one run, or an equirect rendered without Cutpoint's IMU
levelling (an SDK stitch with FlowState or without its sidecar, or a Studio export). Their
`360 qa` results are then not like-for-like with each other or with the director previews,
which render the `.lrv` dual fisheye; for that comparison, export with
`--pano-source dfisheye`. The manifest's `pano` record of each clip notes `levelled` (path
angles used on the input as is) and `flowstate` (`null` when unknown).

## A varied, quality-checked mix

For a day of 360 footage, combine `mix` with the director and QA, and repeat until clean:

```powershell
cutpoint mix trip-360
cutpoint 360 director trip-360 --segments mix_segments.json --preview --out-name mix
cutpoint 360 qa projects/trip-360/pano_paths/mix
cutpoint 360 repair trip-360 --qa projects/trip-360/pano_paths/mix_qa/qa.json
# repeat director, qa and repair until nothing needs repair
cutpoint clips trip-360 --mix
cutpoint 360 qa projects/trip-360/clips_mix
cutpoint 360 repair trip-360 --qa projects/trip-360/clips_mix_qa/qa.json
cutpoint clips trip-360 --mix --force
cutpoint assemble projects/trip-360/clips_mix --loudnorm
```

`360 qa` also counts the frames that `360 director --vl-check` flagged (blocked view or too
little information; stored as `vl` in the path JSON). A clip fails when more than 1 such frame
(`max_vl_bad`) falls inside its span. A clip whose path has no `vl` record (the check was
skipped or unavailable) is judged as before; `qa` does not call Ollama. `qa.json` gets a `vl`
field per clip (`{model, frames, bad, flags}`, or `null`; `frames` counts the frames checked in
the whole director segment, while `bad` and `flags` count only those inside the clip) and
`vl_checked` and `vl_bad` in the edit totals. The log table has a `vl` column (`bad/frames`)
and, when any clip was checked, a summary line. `qa` still exits `0`; a failing clip is a
per-clip result. `repair` does not act on VL flags: a clip that fails only on them is kept as
is; re-plan or drop it by hand.

The horizon check of `360 qa` measures what was rendered: it replays the `v360` rotation
commands of each clip (the `.cmd` file next to its path JSON, or next to a director preview)
and checks where the true up from the camera's IMU lands in the picture. A render bug that
tilts the picture (wrong levelling, a wrong command or one sent for the wrong frame) shows as
tilt. A clip fails when the 95th percentile of the tilt is over 12 deg (`max_horizon_p95`);
frames over 12 deg (`tilt_deg`) are flagged `tilt`. The levelling is relative to the clip's
average attitude, so a tilted mount is fully levelled; only changes within the clip show, at
30 % of the camera's lean by design (`pano.level_strength` 0.7), so some tilt is expected. That
lean is capped at 30 deg (`pano.max_follow_deg`), so a fall or the camera being handled shows
at most 9 deg. Clips
rendered before this check (their `.cmd` file has no `# cutpoint-v360` first line) and still
views without commands fall back to the old prediction from the renderer's own model, which
cannot catch render bugs; an INFO line names them, and re-rendering fixes it. Each clip's
`horizon` in `qa.json` says which was used (`source`: `commands` or `model`). The geometric
check (`360 qa --paths`), which needs no rendered clip, uses the prediction.

The wearer's own head, goggles, gloves and body are *self* boxes: they count as `occluded`
when large, never as the subject or an edge cut. On rendered clips `360 qa` finds them with
the wearer cone when it can, the same geometry `--paths` and the director use: a person box
whose centre, seen through the rotation the clip was rendered with (its `.cmd` commands, else
the renderer's model), lies within 50 deg of the clip's wearer axis is the wearer. That needs
the clip's director path with its `source`, the cached IMU orientation and 360 view layer of
that source, and a render levelled with the IMU (dual fisheye, or an SDK stitch without
FlowState). The own-body CLIP classifier still runs, and a box either one tags is self
(`self_method` `cone+clip`). The cone catches the wearer at the frame edge, which CLIP
misses; keeping CLIP keeps its catches outside the cone (gear held out, a shadow) but also its
mistakes: a close friend CLIP calls self stays self, so is never an edge cut or too close.
Without the cone (a FlowState stitch or Studio export, a clip without a path) CLIP alone tags
them (`clip`). Each clip's `self_tags` in `qa.json` counts the boxes each method tagged
(`cone` is `null` without it), to judge the two.

`360 qa --paths` drops a projected person mostly outside the view (as the detector would miss
it), but still flags `edge_cut` for it when it covers `edge_side_min_area` of the frame at the
side edge, or when it would be the largest person in the frame and at least `size_min_h` tall:
on a rendered frame that person is the subject, which counts as cut at any size. At the left
and right edges `--paths` counts people from `edge_side_min_area` (0.075 of the frame, the
rendered QA's `edge_min_area` of 0.10 over 1.34): a person cut by the side edge is detected on
the rendered frame about 1.34 times as large by area as its projected box. Its `qa.json`
records that floor in `thresholds`; the rendered QA keeps 0.10 there.

Each clip in `qa.json` records how it was rendered, so a run on the director previews and one
on the final clips can be compared: `mode` (`sdk`, `studio` or `dfisheye` for clips, `proxy`
for previews rendered from the `.lrv`), `imu_levelled` (levelled with the IMU track, so the
wearer cone and the measured horizon apply), `levelled` (path angles used on the input as is:
FlowState, sidecar-less and Studio equirects), `flowstate` (`true`, `false`, or `null` when
unknown), `input` (the file name of the render input, no folder) and `cmd_every`; `null` where
the clip does not say (a path without its video). Clips also record `selected`: the moment
`clips` picked, before tails and padding (`null` for previews, whose `segment` is that
moment, and for clips exported before this version). The edit summary adds `by_mode` and
`by_self_method`: per value `clips`, `frames`, `duration` and the `edge_cut` share
(duration-weighted, as `share`; `unknown` for clips of an older `qa.json`).

### Where the two QAs disagree

`360 qa <dir> --compare RENDERED PATHS` reads the two `qa.json` files of the same folder (in
either order: the `mode` in each says which is which), joins them per clip (by file name
without extension) and per frame time, and writes `edge_gap.json` next to the rendered
`qa.json`. It runs no QA and loads no models; `--fps`, `--size` and `--json-only` are ignored
and `--paths` is refused. Run both QAs at the same `--fps`: frames pair only where their
times meet, and a WARNING (`qa_fps_mismatch` with `--json`) says when they differ.

```powershell
cutpoint 360 qa projects/trip-360/clips_mix
cutpoint 360 qa projects/trip-360/clips_mix --paths
cutpoint 360 qa projects/trip-360/clips_mix --compare projects/trip-360/clips_mix_qa/qa.json projects/trip-360/clips_mix_paths_qa/qa.json
```

Per clip and for the edit, `edge_gap.json` counts the joined `frames`, the frames each QA flags
`edge_cut` (`rendered_edge`, `paths_edge`), those both flag (`both`) and those only one flags
(`rendered_only`, `paths_only`). The rendered frame's cut boxes are those
`360 qa` counts for its `edge_cut` (people of a tenth of the frame or more, or the largest
person when at least `size_min_h` tall, touching an edge); the projected boxes include those
the paths QA dropped as mostly outside the view (`slivers` of its frames). Each
`rendered_only` frame gets one cause, the first that applies:

| Cause | Meaning |
|---|---|
| `unpaired` | The paths QA has no frame at that time (another `--fps`, or a shorter clip) |
| `wearer_overlap` | The cut box covers the wearer as the paths QA projects it, in full or as a sliver: the rendered QA did not tag the wearer as self |
| `yaw_offset` | The matching projected box would touch the edge once moved by the clip's median offset between rendered and projected boxes (`median_dx`, a share of the frame width) |
| `stale_view` | The paths QA's boxes come from a view frame more than 0.5 s away (`stale_view_s`), or none within 1 s |
| `no_projected_box` | No projected box overlaps the cut box: the proxy's detector missed the person |
| `other` | A projected box is there, from a recent view frame, but not counted as cut; `other_detail` says why (below) |

An `other` frame gets an `other_detail`, the first of these that applies to the projected box
that overlaps the cut box most (the paths QA's own edge-cut rule replayed on its frame):

| `other_detail` | Meaning |
|---|---|
| `paths_top_edge` | Both touch the top, but the projected box is not taller than `edge_top_h` or reaches `edge_top_max_y2` (or it is a large dropped box at the top: those count at the side edges only) |
| `paths_inside_margin` | The projected box misses the edge by less than 3 % of the frame width |
| `position_mismatch` | It lies farther inside and the cut box has twice its area or more, but it is a dropped box (a sliver, cut at the bottom of the view) about as wide as the cut box (within 25 %) whose centre is more than 5 % of the frame width to the side: the same person, shifted |
| `rendered_box_larger` | It lies farther inside, and the cut box has twice its area or more: a detection or size mismatch |
| `paths_inside` | It lies farther inside at a similar size: a position mismatch |
| `paths_below_size` | It touches the edge but is under `subject_min_h`; or it is the paths frame's largest person but under `size_min_h`; or the cut box counted as the rendered frame's largest person and the projected box is under `size_min_h` |
| `paths_self` | It shares `edge_self_overlap` of its area with a box the paths QA tags as the wearer (the wearer detected twice); the cut box does not |
| `paths_below_area` | It is not the paths frame's largest person and is under the paths `qa.json`'s `edge_min_area` (`edge_side_min_area` at the side edges), while the cut box has the rendered `qa.json`'s `edge_min_area` or more (counted by its area) |
| `paths_not_subject` | The cut box counted as the rendered frame's largest person, but in the paths frame another person is larger |
| `unexplained` | The paths rule would count it: the two reports do not fit together |

Every `rendered_only` frame also has an `evidence` block to read it by: the cut box
(`rendered_box`, `rendered_area`) and the `edge` it touches (`left`, `right` or `top`), the
projected box behind the cause (`paths_box`; `paths_kind` `box`, `sliver`, or `wearer` and
`wearer_sliver` for `wearer_overlap`), its `paths_h` and `paths_area`, and its distance to that
edge (`edge_gap`, a share of the frame width, or height for the top). Values are `null` where
there is no such box.

Each clip adds `other_detail` counts. The edit totals add `causes` and `cause_share` (of the
`rendered_only` frames), and `other_detail` and `other_detail_share` (also of the
`rendered_only` frames, so they add up to the `other` share); `unmatched`
lists the clips in only one report. Each clip also names its rendered `mode` and
`self_method`, and the edit totals count `clips`, `frames`, `rendered_edge`, `paths_edge` and
`rendered_only` by those (`by_mode`, `by_self_method`; `unknown` for an older rendered
`qa.json`), so a gap that comes with one render source shows. Each `rendered_only` frame also
says `in_selected`: whether it lies in the moment that was picked (the clip's `selected` span,
without its tails and padding; else the path's `segment`, as for previews and older clips;
`null` when the reports do not say). The director plans and checks the tails like the moment,
so their frames get a cause like any other; each clip and the edit count them as
`outside_selected`. That needs reports written by this version (clip `offset` and `segment`;
for the tails of clips, `selected`); likewise `stale_view` needs paths frames with `view_dt`
and the sliver matches frames with `slivers`; with older reports those are not found.

Each clip and the edit also get `size_ratio`: the median `width` and `height` of the rendered
boxes over the projected boxes they match (overlap of 0.3 or more after the `median_dx` shift)
and the number of `pairs`, with `null` ratios under 5 pairs. A ratio above 1 means the proxy's
boxes are smaller than the rendered ones (the director's `near_box_scale` can make up for that).

`repair` adds the unclean frames to `mix_exclude.json`, which `mix` reads on the next run. A
repaired clip is cut to its longest clean part if that is at least three quarters of the
category's minimum length, otherwise dropped and the time refilled.

`--segments` can also be a file not written by `cutpoint mix`, such as a hand-written one
(`[{source, start, end, label}]`, as for `clips --segments` and `360 director --segments`). Its
clips are trimmed or dropped the same way (a clip without `category` must keep at least 2.5 s),
but nothing is refilled, and the length budget and content QA of a mix are skipped. A segment keeps its own `id` (for example `h001` copied from
`highlights.json`); one without `id` is named `s001`, `s002`, ... by its place in the list in the
report (`s002b` if a user id already uses `s002`), and the written file gets no `id` added.
Two segments with the same `id` are an error naming both. Relative `source` paths resolve against
the segments file's folder, as for `clips`; exclusions are written with the absolute path (a
relative one left by an earlier version is taken against the folder of its `mix_exclude.json`).
On Windows, a drive-relative path such as `D:clip.insv` is an error; give the full path.
In `mix_exclude.json` such an exclusion is ignored with a WARNING (the rest of the file loads, and
`repair` keeps the entry in the file when it rewrites it); give the full path (`D:\...`) or one
relative to the file's folder. An exclusion matches a segment when their resolved paths are the
same, so symlinks and spellings such as `a/../b` match; `mix` matches its exclusions the same way.
`mix` also matches carried segments and `telemetry.json` start times this way, `repair` matches
crash impacts this way, and `repair` stores one exclusion for a span even if it was stored before
under another spelling.

`--out` writes the repaired list, and `mix_exclude.json` next to it, to another file; a missing
folder is created. `--out` must name a file, not an existing folder.

## Camera paths of the candidates

At its end, `360 analyze` plans the 16:9 director path of every 360 candidate in
`highlights.json` and keeps it in `<project>\pano_candidates\` (one JSON per candidate), so
a preview can show the moment through the virtual camera and flag a poor path before export.
It reads the cached view, voice and orientation layers and decodes no video; the log line
`Director paths: ...` gives the count and the time it took. A candidate whose path fails gets
a WARNING and the analysis goes on. With `--json`, `candidate_paths` has the folder, the counts
(`candidates`, `computed`, `cached`, `skipped`, `failed`, `seconds`) and `flags`: the number of
candidates per flag.

`clips` reuses a cached path when the clip's span, the moment kind, the director settings
(`pano.director`), 16:9 or 9:16, the cached layers and Cutpoint's planning code are exactly
those it was planned with; otherwise it plans the path as before. A clip whose start or end
moved (smart tail, event tail, padding, the speech-aware pass, a trim) is planned anew. The log
says which: `<clip>: director path planned by 360 analyze` for a reused path, else
`<clip>: director path re-planned (<reason>)` with `span differs from 360 analyze`,
`9:16 not planned by 360 analyze` (under `--vertical`: `360 analyze` plans 16:9 only),
`settings changed`, `layers changed` or `planning code changed`. The folder belongs to
Cutpoint: each analysis removes the files of candidates it no longer lists. Do not edit them;
edit the clip paths below.

Each file has a `diagnostics` block (shares are of the candidate's span, 0-1):

| Field | Meaning |
|---|---|
| `quality` | `score`, `pass` and `fails` of the path's geometric direction QA (as `360 qa --paths`) |
| `above_horizon` | The view centre is above the horizon |
| `sky` | The horizon is at or below the frame's lower third line: two thirds of the picture or more is above it |
| `peak_yaw_rate` | Fastest pan within a shot, deg/s (hard cuts excluded) |
| `yaw_travel`, `yaw_travel_per_min` | Total pan within shots, deg and deg per minute (hard cuts excluded) |
| `net_turns` | Largest net rotation in one direction within any 30 s (the whole span if shorter), in full turns: the range of the yaw turned within shots in that window |
| `cuts`, `cuts_per_min` | Hard cuts inside the span |
| `wearer_in_view` | The wearer (the clip's wearer axis) is inside the frame (selfie shots excluded) |
| `off_target` | The view misses a direction that scores clearly better than the one it shows (selfie shots excluded) |
| `flags` | Stable codes of what looks poor, below |

| Flag | When (provisional threshold) |
|---|---|
| `sky` | `sky` above 0.2 |
| `whip` | `peak_yaw_rate` above 55 deg/s (the QA's `max_pan_max`) |
| `spin` | `net_turns` of 1 or more (a full turn one way within 30 s), or `yaw_travel_per_min` above 540 (9 deg/s on average) with at least 360 deg of `yaw_travel` (one quick pan is not flagged) and `net_turns` of 0.5 or more (gentle sweeps back and forth are not flagged): a camera that keeps turning without whip pans |
| `cuts` | 2 or more hard cuts and more than 6 per minute (one cut in a short span is not flagged) |
| `wearer` | `wearer_in_view` above 0.25 |
| `off_target` | `off_target` above 0.4 |
| `qa_fail` | the geometric direction QA fails |

The thresholds are provisional and will be tuned on footage with known-bad director cuts; the
flag codes stay. Angles are those of the director's display frame (levelled by the IMU).

### Preview API (Python)

For a moment preview (the `cutpoint ui`), `cutpoint.pano.candidates` reads these files and plans
what is missing; nothing needs the folder layout:

- `candidate_path(project, id)`: one candidate's cached `path`, `diagnostics` (with `reasons`)
  and `current` (whether `clips` would reuse it).
- `candidate_flags(project)`: per candidate id with a cached path, `file`, `flags`, `reasons`
  (code -> text), `diagnostics` and `key`, a 12-character hash of the cached path that changes
  whenever the path does (use it to name a rendered preview). No freshness check.
- `preview_path(project, source, start, end, *, vertical=False)`: `{"path", "kind", "reason"}`.
  `kind` is `cached` (the path `360 analyze` planned, reused as `clips` would; `reason` None),
  `planned` (planned now as `clips` would, with the moment kind of the candidate overlapping the
  span most; `reason` says why the cached path is not used; not written to the folder) or
  `level_forward` (the director cannot plan: footage offline, no IMU, bad `pano.director`
  settings; a constant forward view at the director's default pitch and wide FOV, levelled by
  the IMU, or for the upright mount (path `level: upright`) when the clip has no orientation
  track; never the raw fisheye; planned, as a director path, over the span and up to 10 s on
  either side; `reason` says why: `footage offline (...)` only when the source itself cannot be
  stat-ed or opened, `missing file: <name>` for another missing file such as a model). It raises
  `ValueError` only for a source that is not a 360 clip of the project or an empty span. It is
  safe from worker threads: calls on the same clip run one at a time, calls on different clips
  in parallel.

  Offline footage: `preview_path` stats the source (the `.lrv`, through `source_remap`) for
  every kind, since the cache folders of its layers and the freshness of a cached path are keyed
  by its size and modification time; on Linux and macOS the source's folder may also be checked
  once per process for case-insensitive names. When the orientation track is not cached yet it
  looks up the `_00_.insv` next to the clip (which may list that folder) and reads its IMU
  trailer. An unmounted source fails fast (`level_forward`, `footage offline`); a hung network
  mount blocks the calling thread in that stat, so call it from a worker. `candidate_flags`
  reads only the project's files (plus that one folder check).
- `preview_key(path, *, vertical, fmt, settings)`: a 16-character hash to name a rendered
  preview, the same on every run and OS. It covers the path (`path_id`), `vertical`, the
  `Format360` (width, height, fps), a preview version and, of `settings` (the `pano` section of
  config.json), the keys a preview's pixels depend on: `imu_offset_s`, `level_strength`,
  `tilt_follow_s` and `max_follow_deg`. Other settings leave it unchanged (`pano.director`
  changes the path itself; previews render the unlevelled `.lrv` with `cmd_every=1`, so
  `equirect_yaw_offset` and `cmd_every` do not apply).

`cutpoint.pano.render.render_segment(clip, path, start, end, out, ..., progress=None)` renders
any of these paths. `progress` is called with the rendered fraction from ffmpeg's progress
output: rising values below 1.0 at most about 10 times a second (from a helper thread, never two
calls at once), then exactly one 1.0 once the file is complete, and never after the call
returns. A callback that raises is logged once at DEBUG and dropped; the render goes on.

## Editing the camera path

Each rendered clip's path is saved as plain JSON in
`<project>\pano_paths\<clips folder>\<clip name>.json`. The `keys` hold `t`, `yaw`, `pitch`,
`fov`, `target` and `cut` (yaw 0 = forward, positive = right; pitch positive = up; degrees).
Yaw 0 is where the camera's front points on a helmet mount; for a clip filmed with the camera
upright (lenses horizontal) it is the `_10_` lens axis, and the path has `"forward_axis": "+z"`
(and `"det_frame": "-z"`: its views were sampled with yaw 0 on the `_00_` lens, then relabelled).
Edit them and re-run `cutpoint extend`: it reuses the recorded path when it covers the new
range (its `fixed` span: the moment and up to 10 s on either side), so hand edits are kept. A
path from an older version (4) is reused only within its moment (`segment`); a longer range
plans it anew with a WARNING, and the old file is kept as `.bak`.

## Limits

- Rendering runs at roughly 0.35-0.5 times realtime.
- There is no rolling-shutter correction; levelling removes rotation only.
- The wearer is sometimes framed as a friend when seen from the side.
- 4K-mode clips render at lower resolution than 5.7K-mode clips.
- Crash detection uses only the wearer's IMU; a friend's fall is found through the transcript.
- Clip start times come from the file name and are read in the PC's time zone.
